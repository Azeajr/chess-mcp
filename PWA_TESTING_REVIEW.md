# Browser and PWA testing: verified findings and reduced plan

Audited 2026-09-04 against working tree `6ceca328116aec3f4811227dac8afb98fb0d44d3`.
This supersedes `BROWSER_SUPPORT_RESEARCH.md`, `PWA_TESTING_FINDINGS.md`, and
`PWA_TESTING_STRATEGY.md`. Those drafts were removed at the user's request; repeated claims are
adjudicated together below. Findings and claim verdicts describe the pre-fix audit state.

## Implementation follow-up (2026-09-05)

The three reduced-plan changes are implemented in the working tree:

- `openings.tsv` is precached. Production assertions cover the manifest and offline assets;
  the lifecycle harness covers offline reload, saved document restoration and editing, a fresh
  engine worker, opening lookup, and online-only evaluation unavailability. Its flagged A/B
  builds use temporary output directories, preserving the ordinary deployment artifact.
- Network test teardown restores fetch and fake timers even after failure. Announcement reset
  is awaitable, and its browser callers wait for completion.
- CI and deployment call the same [UI validation workflow](.github/workflows/ui-checks.yml).
  Deployment requires successful validation and downloads that run's revision-named artifact.
  Both configured push branches and manual dispatch use this dependency; Node 26 is used throughout.

The production build assertions, expanded offline/update lifecycle, 40 network tests,
all-package typecheck, and workflow lint passed in the implementation session. Follow-up validation
passed 117 container browser tests across three engines, 397 UI unit tests, and core-test TypeScript
compilation. Detailed completion evidence is tracked in [the handoff](PWA_IMPLEMENTATION_HANDOFF.md).
No hosted deployment or native OS installation was performed.

## Findings that survive verification

1. **Keep the existing testing architecture.** Node's test runner with `tsx`, Playwright browser
   tests, generated-build assertions, and a real build-A/build-B service-worker test already exist.
   Vitest is absent; `workbox-window` is already a UI dependency. No new testing framework is needed.
   The real update test passed, as did 36 repeated update-UI executions across the three engines.
   [Packages][packages], [UI package][ui-package], [build test][build-test], [lifecycle test][lifecycle].

2. **Offline opening data is a confirmed defect; broader offline behavior lacks regression coverage.**
   `/openings.tsv` is copied into the build and fetched by browser commands, but the precache glob
   excludes TSV and no runtime caching rule covers it. In both host Chromium and the canonical
   Playwright image, it returned HTTP 200 online and failed to fetch after an offline reload.
   Its browser loader converts that failure into an empty opening table. In the same fresh-context
   probes, the cached app rendered and a newly started Stockfish worker returned a depth-1 best move.
   Existing tests do not disconnect the browser and check these behaviors.
   [Asset copying][assets], [PWA configuration][vite], [opening loader][openings].

3. **Build metadata checks do not prove installation on every platform.** The emitted manifest has
   `start_url: "/"`, `scope: "/"`, standalone display, and one SVG icon with `sizes: "any"`.
   Chromium 151 reported no installability errors for it; missing PNG icons are therefore not a
   demonstrated failure here. Actual OS installation, launch from an installed icon, and other
   platforms were not tested. The app has no custom install prompt. `registerType: "prompt"`
   controls update acceptance. [Configuration][vite], [registration][updates], [update semantics][prompt].

4. **The browser matrix is real, but its costs and failure causes were overstated.** Current discovery
   lists Chromium 236, Firefox 228, WebKit 205 tests; these are collected cases, not pass counts.
   Firefox/WebKit exclude `@visual` and `@engine-bound`; WebKit also excludes the entire findings
   spec, currently 23 otherwise-selected cases. Historical logs verify two WebKit failures, not
   that WebKit is expendable or that either timeout's cause is known. Keep the matrix for now;
   use an explicit Chromium project for routine local iteration. [Configuration][playwright],
   [historical run A][run-a], [historical run B][run-b].

5. **Fetch-stub leakage is confirmed; the alleged current keyboard failure mechanism is not.**
   All four network suites leave `globalThis.fetch` replaced; their 38 tests nevertheless passed.
   This is a test-isolation defect, not evidence that it causes browser flakes. The keyboard case
   passed all nine fresh container executions. The helper's broad gridcell focus check remains,
   but source inspection also found an asynchronous announcement reset whose bridge discards its
   promise. Neither mechanism was demonstrated to cause a failure in this audit. Selection and
   history insertion themselves are synchronous, so a delayed-announcement explanation is not
   established. [Fetch helper][fetch-helper], [keyboard spec][keyboard], [reset bridge][entry],
   [selection][cursor], [announcement store][announce].

6. **Existing deterministic UI checks remain useful; no new accessibility program is justified here.**
   The real screen-reader evidence pipeline was removed, but nine current specs directly import
   the accessibility helper. Keyboard, geometry, contrast, semantics, reduced-motion, and dedicated
   UI checks remain. Removal history also records the real macOS focus defects that pipeline caught;
   its retirement does not prove it provided no assurance. [Helpers][accessibility], [removal][removal].

7. **Deployment exists and is independent of CI completion.** `ci.yml` defines four jobs, with six
   E2E shards and a host-based Chromium PWA lifecycle check. `deploy-ui.yml` separately builds and
   deploys to Cloudflare Pages on selected pushes or dispatch; it does not wait for those CI jobs.
   Its Node version is 22, while CI specifies 26. Adding a check to CI alone does not make that
   check a deployment prerequisite. [CI][ci], [deployment][deploy].

## Reduced plan

These are the accepted implementation requirements, ordered by evidence and impact. The follow-up
above records their implementation; the original acceptance conditions are retained below.

| Work                                  | Smallest useful change                                                                                                                                                                                                                                                                                      | Acceptance / stop condition                                                                                                                                                                                                                                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Protect the offline contract       | Add `openings.tsv` to precaching; extend the existing production PWA tests. Cover a controlled offline reload, a fresh engine worker, document restoration/local editing, and opening lookup. Check manifest start URL/scope, referenced assets, engine JS/WASM, and the opening table in the built output. | First demonstrate the missing-table failure; after the change, offline opening lookup returns a known fixture result, engine evaluation succeeds, and saved document state survives. Existing A→B waiting/deferral/Later/Reload checks still pass. Run in `ui-checks`; keep the ordinary dev-server suite separate. |
| 2. Close test cleanup gaps            | Restore fetch and fake timers through failure-safe teardown in the four existing network suites. Make the announcement-reset bridge awaitable by its callers.                                                                                                                                               | A subsequent test observes the original fetch even after a failing test; announcement reset is complete before the caller continues. All 38 network tests and the focused keyboard/update tests pass. Do not claim this fixes the historical keyboard flake without reproduction.                                   |
| 3. Make deployment assurance explicit | If these checks are intended to protect the shipped PWA, make successful validation of the same revision a prerequisite of the existing deployment workflow. Align the build runtime with the validated runtime.                                                                                            | A failing required PWA check prevents that revision from deploying; the validated revision is the one deployed. A workflow review must also cover manual dispatch and both currently configured push branches. No new audit service is needed.                                                                      |

Retain the current browser exclusions pending a focused remeasurement. If the keyboard failure
recurs, capture focused square, selection, reset completion, and announcement history before
changing assertions. If revisiting the WebKit exclusion, run the two named cases in the container
with traces and a measured test budget, then narrow the exclusion only when supported by results.
Neither investigation needs to block the confirmed offline fix.

For installability, keep a small manual check on the actual browser/OS the user installs on:
install through browser UI, launch standalone, reopen offline, and accept an update. Record the
platform/version and result. Add an icon fallback or custom install UI only for a demonstrated
need. Do not treat a synthetic `beforeinstallprompt` event as proof of installation.

Do not add Lighthouse PWA gates, mock tests for generated Workbox internals, new test directories,
push/background-sync features, dashboards, nightly audit infrastructure, or screenshot baselines
for browser-owned installation UI. None follows from the verified gaps. General performance
profiling can be considered separately if a concrete loading problem or budget is established.
