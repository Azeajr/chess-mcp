## Implementation approach

After `WP-033` ships, keep one workspace and run two automated journeys: a review journey ending in a decision and a redesign journey ending in an applied change set. The review journey must never enter redesign state without the explicit redesign action; the stage indicator must equal application state after every transition; the redesign journey must reach apply without duplicate resolution controls. Record the deterministic results and retain the no-split decision. Subjective clarity is not claimed.

## Acceptance criteria

- A machine-generated journey report records both transition traces, stage-state equality, explicit redesign-entry count, duplicate-control count, and pass/fail against the fixed thresholds. No production code changes and no split proposal are part of this package.

### Fixed thresholds

The plan requires "fixed thresholds" but never stated numbers, and the manifest's "layout/interaction complexity budgets" were likewise undefined. Inventing a clicks-per-task budget would be an implementation-invented standard, so the thresholds below are exactly the quantities `PD-5` rests on — each is a count, not a judgement — and `scripts/wp035-strategic-fit-journeys.mjs` fails closed on any deviation.

| Metric                            | Review | Redesign |
| --------------------------------- | ------ | -------- |
| `decisionCount`                   | 1      | —        |
| `confirmableAcceptanceCount`      | —      | 1        |
| `explicitRedesignEntryCount`      | 0      | 1        |
| `implicitRedesignEntryCount`      | 0      | 0        |
| `stageStateMismatchCount`         | 0      | 0        |
| `duplicateControlCount`           | 0      | 0        |
| `maximumHorizontalOverflowPixels` | 0      | 0        |

`implicitRedesignEntryCount` counts transitions where the Replacement Lab _became_ open without an explicit action, not transitions where it merely remained open; the lab legitimately stays open across the steps that follow. Every Replacement Lab state projects onto the workspace's `evidence` stage, because the lab is a nested dialog above the workspace rather than a workspace stage of its own.

### Scope correction — the redesign journey's end state

The approach above says the redesign journey ends "in an applied change set". The browser journey ends one step earlier, at a **revision-bound, confirmable atomic acceptance**, for a reason that is a property of the acceptance contract rather than a gap in the test:

`snapshotMatches` (`apps/ui/src/store/strategic-fit-changes.ts:410`) validates a nine-link identity chain before any acceptance is allowed. `tree_identity` and `metadata_identity` are hashes of the _live_ document, and the staged change set must apply cleanly to the live tree. Only `stageChangeSet` produces those identities, from a change set constructed by `packages/chess-tools` against that exact tree. Neither is reachable from a browser test without adding a production DEV seam, which is outside this package's `docs/`-only allowed files. Injecting an `"accepted"` presentation state instead would produce a report asserting an applied change set that never happened — precisely the fabricated evidence `AUTOMATED_COMPLETION.md` forbids.

The applied outcome is therefore proven where the machinery lives: `apps/ui/test/strategic-fit-changes.test.ts` stages through the real change controller, accepts, and asserts the document revision increments by exactly one. The browser journeys prove the redesign path's reachability, its single explicit entry, and that reaching acceptance mutates nothing; that test proves the apply. Neither claims the other's evidence, and the report records the division.
