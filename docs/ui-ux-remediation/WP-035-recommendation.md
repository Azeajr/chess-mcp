# WP-035 — Review/Redesign split: recommendation

**Recommendation: retain one workspace. Do not split Strategic Fit into two modes.**

This is the validation checkpoint for `PD-5`, not a research study. The audit suggested _considering_
a Review/Redesign split and was explicit that it is not an automatic implementation requirement, and
that `WP-033`'s stage strip might already resolve the overload it was reacting to. This package
measures whether it did.

## What was measured

Two instrumented journeys run through the single workspace on every suite run
(`apps/ui/test/e2e/strategic-fit-findings.spec.ts`, the `WP-035` tests). Every transition records
the application's own stage, the visible stage indicator, the per-selector resolution-control
counts, whether the redesign surface is open, and horizontal overflow.

| Metric                            | Review | Redesign | Threshold |
| --------------------------------- | ------ | -------- | --------- |
| Decisions reached                 | 1      | —        | 1         |
| Confirmable acceptances reached   | —      | 1        | 1         |
| Explicit redesign entries         | 0      | 1        | 0 / 1     |
| **Implicit redesign entries**     | **0**  | **0**    | 0         |
| **Stage-state mismatches**        | **0**  | **0**    | 0         |
| **Duplicate resolution controls** | **0**  | **0**    | 0         |
| Horizontal overflow (px)          | 0      | 0        | 0         |

The machine-generated trace is
[`reports/WP-035-strategic-fit-journeys.json`](reports/WP-035-strategic-fit-journeys.json),
regenerated by `node scripts/wp035-strategic-fit-journeys.mjs`. The generator validates every metric
against the thresholds and **fails closed**: a failed run or any deviation leaves the committed
report untouched and exits non-zero, so the report can never describe a run that did not pass.

## Why the measurements support no split

The case for splitting was that one workspace asks users to hold review and redesign in mind at
once. Three measured facts undercut it:

1. **Review never slides into redesign.** The redesign surface did not appear once across the review
   journey, and in the redesign journey it appeared only on the transition that explicitly opened
   it. Entering redesign is an act, never a drift — which is the separation a split would buy,
   already present without one.
2. **The stage indicator never disagreed with the application.** At every transition exactly one
   stage was marked current and it equalled the application's own stage. The progression model
   `WP-033` added is doing the work the split was meant to do.
3. **No control was ever rendered twice.** The duplicate-render defect `WP-033` removed — resolution
   actions appearing in two places at once — was the concrete form of "this workspace is
   overloaded". It is gone, and this is now a standing regression gate rather than a one-off fix.

No follow-up split package is proposed. Subjective clarity is **not** claimed: these are counts, not
preference evidence, and nothing here measures whether users find one workspace pleasant. A future
separately authorized research initiative could still revisit `PD-5`; this package does not.

## Scope note — the redesign journey's end state

The browser journey ends at a revision-bound, confirmable atomic acceptance rather than at a mutated
repertoire, and the reason is a property of the acceptance contract rather than a gap in the test.

`snapshotMatches` (`apps/ui/src/store/strategic-fit-changes.ts:410`) validates a nine-link identity
chain before allowing acceptance; `tree_identity` and `metadata_identity` are hashes of the _live_
document, and the staged change set must apply cleanly to the live tree. Only `stageChangeSet`
produces those identities, from a change set `packages/chess-tools` constructs against that exact
tree — neither reachable from a browser test without adding a production DEV seam, which is outside
this `docs/`-only package. Injecting an `"accepted"` presentation state instead would make the
report assert an applied change set that never happened, which `AUTOMATED_COMPLETION.md` forbids.

The applied outcome is proven where that machinery lives: `apps/ui/test/strategic-fit-changes.test.ts`
stages through the real controller, accepts, and asserts the revision increments by exactly one. The
journeys prove the redesign path's reachability, its single explicit entry, and that reaching
acceptance mutates nothing. Neither claims the other's evidence.
